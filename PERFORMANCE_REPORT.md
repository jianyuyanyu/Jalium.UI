# Jalium.UI Performance Audit Report

- Audit date: 2026-07-28
- Baseline: `f439cc77066e20ebeeeb94f891a3fe978bf82460`
- Configuration: native Release (`-O3 -DNDEBUG` benchmark driver), WSL2 Ubuntu 24.04.4 LTS

## Outcome

One performance defect met the audit's evidence threshold and was optimized: opening an audio file on POSIX buffered the complete file before creating the decoder. The corrected path streams directly through the codec file API.

On a deterministic 115,200,044-byte PCM WAV, 150 measured opens after 10 warmups changed:

| Metric | Baseline | Fixed | Change |
|---|---:|---:|---:|
| Median open latency | 28.701 ms | 0.002 ms | about 14,350x faster |
| P95 open latency | 29.900 ms | 0.002 ms | about 14,950x faster |
| Minimum | 27.408 ms | 0.002 ms | — |
| Maximum | 46.172 ms | 0.003 ms | — |
| Process maximum RSS | 116,224 KiB | 4,096 KiB | -112,128 KiB / about -96.5% |

No GPU, layout, startup, first-frame, or rendering throughput improvement is claimed. Those categories did not receive controlled before/after measurements and remain explicitly unverified.

## Scenario and fixture

The benchmark is `src/native/jalium.native.media.linux/tests/audio_open_benchmark.cpp`.

It:

1. Initializes the Jalium audio subsystem once.
2. Performs the requested unmeasured warmup opens.
3. For each measured sample, records only `jalium_audio_decoder_open_file` using `std::chrono::steady_clock`.
4. Verifies that a decoder is returned, queries valid sample-rate/channel metadata, and closes it.
5. Sorts all samples and reports median, nearest-rank P95, minimum, and maximum.

The fixture is generated by the same benchmark:

| Property | Value |
|---|---|
| Container | RIFF/WAVE |
| Codec | PCM, 16-bit |
| Channels | 2 |
| Sample rate | 48,000 Hz |
| Duration | 600 seconds |
| Payload | deterministic silence |
| File size | 115,200,044 bytes |
| SHA-256 | `72757f6c87b6ee673fcfafd30892c04e7384f54ef8937a20c7ee34fa2c807756` |

This large uncompressed file intentionally magnifies whether decoder open is O(header) streaming or O(file size) buffering. The benchmark measures open only; decode throughput is not part of the claim.

## Root cause

`DecoderOpenFile` routed WAV/FLAC/MP3/Vorbis through `ReadFileToBytes` on every platform. That bridge existed to preserve non-ASCII Windows paths because bundled codec file APIs ultimately use narrow `fopen`, but POSIX accepts UTF-8 paths directly. Consequently every Linux open:

- read the complete file before returning;
- allocated a vector approximately equal to the encoded file size;
- copied/moved that buffer into decoder-owned storage; and
- made open latency and memory scale with the full file rather than its header.

## Implementation

`src/native/jalium.native.media.core/src/audio/audio_decoder.cpp` now:

- calls streaming codec file APIs directly on POSIX;
- calls them directly for ASCII Windows paths;
- keeps the wide-path memory bridge only for non-ASCII Windows paths;
- caps any intentionally buffered audio payload at 512 MiB;
- maps allocation failure to a stable media status instead of allowing an exception across the C ABI.

`src/managed/Jalium.UI.Media/Native/NativeAudioDecoder.cs` converts `TimeSpan` ticks to microseconds with integer division (`Ticks / 10`) rather than a floating-point millisecond round-trip.

## Statistical method and raw summary

The final comparison used:

- 10 warmup opens per binary;
- 150 measured opens per binary;
- identical fixture and filesystem location;
- baseline first, fixed second for the final run;
- median of the sorted 150 samples;
- nearest-rank P95 (`ceil(0.95 * N) - 1`);
- `/usr/bin/time -v` around a 50-iteration/5-warmup process for maximum RSS, because RSS is a process peak and not a per-open statistic.

Final 150-sample summaries:

```json
{"implementation":"baseline","iterations":150,"warmup":10,"median_ms":28.701,"p95_ms":29.900,"min_ms":27.408,"max_ms":46.172}
{"implementation":"fixed","iterations":150,"warmup":10,"median_ms":0.002,"p95_ms":0.002,"min_ms":0.002,"max_ms":0.003}
```

## Reproduction

Build the fixed benchmark:

```bash
cmake -S src/native -B /tmp/jalium-audit-native \
  -DJALIUM_MEDIA_LINUX_BUILD_BENCHMARKS=ON
cmake --build /tmp/jalium-audit-native --config Release \
  --target jalium.native.media.audio-open-benchmark -j"$(nproc)"
```

Generate and verify the fixture:

```bash
/tmp/jalium-audit-output/linux-x64/Release/jalium.native.media.audio-open-benchmark \
  --generate-wav /tmp/jalium-audit-audio-open-600s.wav 600
stat -c %s /tmp/jalium-audit-audio-open-600s.wav
sha256sum /tmp/jalium-audit-audio-open-600s.wav
```

Run the fixed sample:

```bash
/tmp/jalium-audit-output/linux-x64/Release/jalium.native.media.audio-open-benchmark \
  /tmp/jalium-audit-audio-open-600s.wav 150 10
```

For the baseline, create a separate worktree at `f439cc77`, build its Linux media library in Release, then compile the benchmark driver against the baseline headers/library and run the identical command. Do not reuse the fixed library through `LD_LIBRARY_PATH`; confirm the binary's linked/rpath target first.

## Correctness and regression risk

Potential risk is platform path behavior:

- POSIX codec APIs receive UTF-8 paths directly, which matches the platform filesystem contract.
- ASCII Windows paths retain streaming.
- Non-ASCII Windows paths keep the prior UTF-8-to-wide/read-memory bridge, now with checked conversion/allocation and a 512 MiB cap.
- Memory-open callers are also capped at 512 MiB to prevent an alternate unbounded buffer path.

Correctness validation included:

- decoder open and metadata verification on every benchmark sample;
- Linux media smoke tests;
- Windows and Linux full managed suites;
- Windows native Release build;
- Linux native CTest;
- non-ASCII/invalid UTF-8 and ABI boundary tests.

The benchmark does not read decoded frames, so it is paired with the existing decoder/media tests rather than being treated as a correctness test by itself.

## Build throughput observation

The audit also corrected a parallel output race. This is a reproducibility fix, not a claimed speed optimization. After the change, three clean parallel Release solution builds all passed:

| Run | Wall time |
|---|---:|
| 1 | 25.30 s |
| 2 | 23.32 s |
| 3 | 23.95 s |

There is no controlled serial-vs-parallel baseline, so these numbers demonstrate stability only.

## Remaining performance work

The following requested categories were not measured with a controlled Release before/after protocol and therefore have no improvement claim:

- cold and warm process startup;
- main window creation to first frame;
- XAML/JALXAML parse and source-generation throughput;
- theme/resource dictionary load;
- Measure/Arrange counts and latency;
- visual-tree traversal and hit testing;
- binding/property invalidation throughput;
- managed allocation, LOH, GC pause, and long-run handle growth;
- text shaping, rasterization, and glyph-atlas hit rate;
- image decode/resize/upload throughput;
- draw calls, batches, state changes, uploads, barriers, and GPU waits;
- scrolling/virtualization at large data scale;
- multi-window/high-DPI rendering;
- animation, blur, shadow, transparency, and video steady-state frame time;
- cache hit rate, capacity, and eviction cost.

These should be addressed with dedicated BenchmarkDotNet/native harnesses and GPU captures in follow-up changes, one evidence-backed optimization at a time.
